## 1. 仍存在的问题（详细）

### 1.1 【P1】官方 `request` 包裹层未解包

官方复杂工具的入参是 `{ request: { … } }`，本地是扁平 `{ … }`。`mcpProtocolRoute.js:82` 直接取 `params.arguments`，**没有解包**。

```
实测：tools/call competitor_lookup { request: { marketplace:'US', asins:['B07Z82895W'], size:20 } }
返回：{"jsonrpc":"2.0","id":1,"error":{"code":-32602,"message":"marketplace is required"}}
```

**影响**：任何按官方 schema 生成的 MCP 客户端切到本地服务后，**21 个本地工具全部不可用**（参数拿不到）。
**建议**：在 `mcpProtocolRoute.js` 的 `tools/call` 分支里，若 `args.request` 是对象则合并摊平（`args = { ...args, ...args.request }`）。
**待你决策**：这是有意设计（只服务自定义客户端）还是遗漏？若要保持与官方一致，应解包。

---

### 1.2 【P1】`product_node` 的 `month` 完全无效

`month` 在 tools.json 里描述为「查询历史月份类目」，但 handler 只做 `assertMonth` 校验后透传，实际查询的是本地 `amz_category` 表（无月份维度）。

```
实测：
  { marketplace:'US', month:'202508' } → first=1055398 / Home & Kitchen / products=1581481
  { marketplace:'US', month:'202401' } → first=1055398 / Home & Kitchen / products=1581481   ← 完全相同
```

**建议**：二选一 —— ① 补历史月份数据源；② 在 tools.json 移除 `month`（不撒谎）。

---

### 1.3 【P1】`traffic_listing_stat` 与官方入参不一致

| 入参 | 官方 | 本地 |
|---|---|---|
| ASIN | `asin`（单个，必填） | `asinList`（数组，必填） |
| 月份 | `month` | **无此参数** |

```
实测：
  { marketplace:'US', asinList:['B07Z82895W'] }                  ✓ 返回 relations=1823
  { marketplace:'US', asin:'B07Z82895W' }                        ✗ -32602 asinList is required
  { marketplace:'US', asinList:['B07Z82895W'], month:'202508' }  ✓ 但结果与不传 month 相同（无变化）
```

**附带问题**：响应里 `asin` 字段为 `null`（未回显请求的 ASIN）。
**建议**：兼容 `asin`（单数）与 `asinList`（数组），补 `month` 并确认上游是否支持。

---

### 1.4 【P1】`keyword_conversion` 响应 `order` 是硬编码

`keywordConversionTransformer.js` 里 `order` 写死为 `{ field: '', desc: true }`（两处：空数据分支与正常分支），handler 也未传 `order`。

```
实测：传 order={field:'searches',desc:false} → 回显 order={"field":"","desc":true}
```

**说明**：官方 `keyword_conversion` 本身**没有 `order` 参数**。所以更合理的做法是**移除响应里的 `order` 字段**，而不是修成能回显。

---

### 1.5 【P1】`competitor_lookup` / `product_research` 响应体无 `order` 字段

```
实测：competitor_lookup  hasOrder=false   order=undefined
      product_research   hasOrder=false   order=undefined
```

两者共用 `competitionTransformer.js`，其返回值只有 `marketplace/page/size/total/pages/hasNextPage/items`。
**建议**：若要与官方对齐，补 `order`（从请求回显）。

---

### 1.6 【P1】`order.field` 无白名单校验（非法值穿透上游）

`competitor_lookup` / `product_research` 直接把 `args.order.field` 字符串发给上游，无枚举校验：

```
实测：order={field:'revenue'}（官方合法值是 reviews，不是 revenue）
返回：{"code":"SERVICE_ERROR","message":"数据服务返回错误: 处理请求出现错误,请稍后重试。",
       "data":{"upstreamCode":"ERR_GLOBAL_500","httpStatus":200,"hint":"请检查请求参数后重试；如持续失败请联系管理员"}}
```

**已改善**：原清单记录的「上游 4xx 被包成 `code=OK`」**已不存在**，现在是 `code=SERVICE_ERROR`。
**仍缺**：没有 `-32602` 白名单拦截，用户看不到「`revenue` 不是合法排序字段」这个真因；且 `data.httpStatus=200` 会误导。
**建议**：对 `order.field` 做白名单校验（参考 `traffic_listing` 的 `ORDER_FIELDS` 做法），非法值直接 `-32602`。
**注意命名不一致**：官方用 `reviews`，本地用 `ratings`（`competitor_lookup.order.field` 描述里列的是 `ratings`）。

---

### 1.7 【P1】`traffic_keyword` 响应缺 `size` / `page`

```
实测顶层字段：marketplace, asin, total, items, stats
官方分页信封：guestId, pages, page, size, total, took, url, order, items, terminal, hasNextPage, guestVisited
```

**建议**：补 `size`/`page` 回显（或明确说明该接口上游不返回分页信息）。

---

### 1.8 【P2】`market_research` 输出字段体系与官方不同（最大一项）

```
本地 item 字段 = 32   官方 item 字段 = 102
官方有·本地缺 = 79    本地有·官方无 = 9
```

- 官方 102 的构成：基础/类目 8 + 缩略图 1 + 大盘汇总 18 + 体量重量利润 16 + **topN 矩阵 36**（4×3×3）+ **新品矩阵 28**（4×7）
- 本地用的是另一套命名：`topAvgUnits`、`monopolyRatio`、`goodsCrn`、`brandCrn`、`sellerCrn`、`newCount`、`newProportion`、`topAvgRevenue`、`topAvgBsr`

**这是「命名体系不同」而非「少几个字段」**，要对齐等于重写 transformer。**产品决策项，建议单独排期**。
